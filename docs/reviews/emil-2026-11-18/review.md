# LAGDA screen review using Emil skills

Reviewed 18 November 2026. The existing production feature set needs accessibility and interaction polish before a visual-quality sign-off. The highest priorities are missing form labels and low-contrast text. The most visible usability opportunity is giving document work priority over upgrade promotions on the Dashboard and Templates screens.

This review creates the [screen improvement roadmap](../../emil-screen-improvement-roadmap.md). It does not request additional features, enable deferred modules, alter plan gates, or authorize deployment.

## Confirmed findings and design recommendations

The Before column describes current behavior. The After column specifies a proposed change, not an implemented fix. P1 is high priority, P2 is medium priority and P3 is low priority.

| Before | After | Why |
| --- | --- | --- |
| **E01 P1, confirmed:** Profile Full name and Display name have visible captions but no associated accessible labels. `ProfilePage.tsx:230` and `:237` omit the `htmlFor` that `SettingsShell.tsx:649` already supports. | Pass stable matching IDs and `htmlFor`; connect helper and error text with `aria-describedby`. Preserve the current form and validation. | Axe reports critical `label` failures on desktop and phone. Captions must be available to assistive technology. |
| **E02 P1, confirmed:** Templates Sort uses an adjacent span instead of an associated label, at `src/app/pages/platform/templates/TemplatesPage.tsx:497`. | Associate the visible Sort label and select with an ID, keeping existing options and behavior. | Axe reports critical `select-name` on desktop and phone. |
| **E03 P1, confirmed:** Active sidebar text is azure on pale blue at 3.74:1. Preparation helper text uses `#8A9BAE`, measured 2.84:1 on white. Account-creation and verification links also fall slightly below 4.5:1 on their pale backgrounds. Public decorative status pills are approximately 2:1. | Adjust foreground/background tokens for actual combinations: at least 4.5:1 for ordinary text and 3:1 for qualifying large text. Preserve status meaning and brand identity. Audit readable active/helper text separately from genuinely disabled controls. | Low contrast recurs across several existing screens. Sources include `PlatformSidebar.tsx:75`, `prepare/PrepareLayout.tsx:53` and `:340`, and `layouts/CreateAccountLayout.tsx:53`. The public pills are decorative but remain visually difficult to read. |
| **E04 P1, confirmed:** Notifications renders `<span aria-label="Unread">` without a role at `NotificationsPage.tsx:184`. | Put meaningful unread text in the notification's accessible name, or add visually hidden text and make the visual dot decorative. | Axe reports serious `aria-prohibited-attr`. This fixes semantics without adding notification behavior. |
| **E05 P2, measured:** Template grid/list buttons are 26px high, sort direction is about 26 by 29px, and the sort select is 30px high on the 390px layout. | Give touch controls approximately 44px activation areas with enough spacing; preserve a compact desktop presentation. Allow the toolbar to wrap without obscuring controls. | Easier phone use and fewer accidental taps. This is a touch-usability recommendation, not a claim that every control violates the WCAG 2.2 24px minimum. |
| **E06 P2, design recommendation:** Free-plan Dashboard shows plan comparisons and a chatbot promotion before the first-document action. Templates places a large chatbot promotion ahead of the library toolbar. | Put existing document actions, status and template library controls first. Reduce promotions to a secondary area; retain current plans, prices and entitlement checks. | On the 390 by 844 Dashboard capture, the first screen is mostly upgrade content. On Templates, the library starts close to the bottom of that screen. Existing work should be easiest to reach. Sources: `components/dashboard/RealDashboard.tsx:501`, `:522`, and `TemplatesPage.tsx:422`. |
| **E07 P2, source and runtime configuration confirmed:** Platform route content always gets a 220ms upward fade through `PlatformLayout.tsx:290` and `styles/theme.css:397`. The same animation rule applies after keyboard-activated route navigation. Shared Button uses `transition-all` at `components/ui/button.tsx:19`; Sidebar animates width at `PlatformSidebar.tsx:282`. | Remove routine page entrances for repeated navigation, especially keyboard navigation. Replace unbounded transitions with explicit properties. Keep sidebar width changes immediate or use a measured alternative that preserves content geometry. Retain reduced-motion support. | Emil's criteria favor immediate frequent actions and bounded motion. Reduced motion already disables the route entrance and should be preserved. No frame-rate regression was measured; sidebar width is a layout-cost risk rather than a proven dropped-frame defect. |
| **E08 P2, confirmed presentation inconsistency:** Preparation step cards say Signers and Order, while page headings say Participants and Routing. Entry copy describes authentication before field placement, while the visible sequence places Fields first. After fields are placed, Review still says Ready for field placement and asks users to check settings before proceeding to place signature fields. | Use one consistent step vocabulary and update help copy to match the existing sequence. Keep broader participant roles clear and preserve the workflow order. | Reduces uncertainty within an existing process. Sources: `prepare/PrepareLayout.tsx`, `PrepareEntryPage.tsx`, `ParticipantsStep.tsx` and `RoutingStep.tsx`. |
| **E09 P3, design recommendation:** An empty template library shows both No templates found and No templates yet, with promotions and filters above the first-template guidance. | Distinguish an empty library from a filtered no-results state; show one clear explanation and the existing Create Template action or Clear Filters action as appropriate. | Makes the next action clearer without adding capabilities. Source: `TemplatesPage.tsx`, result-count block around line 580 and existing empty state. |

## Coverage and limits

The main pass captured 27 route/viewport attempts. Additional passes checked unauthenticated mobile sign-in and account creation, uploaded-draft preparation, participant editing, routing, settings, fields, authentication, review and authorization. These cover public landing, pricing, public verification, authentication, Dashboard, Documents, Templates and gallery, Contacts, Notifications, authenticated verification, Profile, Security, preparation upload, participants, routing, settings, fields, authentication, review and authorization. All 27 main-pass document-width checks showed no page-level horizontal overflow; that does not prove every nested panel or off-screen control fits. The main pass recorded no uncaught page errors. Mobile sign-in and desktop sign-in, password reset and pricing returned no axe violations under the selected rules in those captures.

Some attempted routes redirected: the billing attempt returned Security; the raw document-ID detail attempts returned Documents; authenticated mobile sign-in returned Dashboard. Those captures do not count as billing, request-detail or unauthenticated sign-in coverage. The separate mobile-auth pass corrected the last coverage gap.

The preparation pass saved one fictional participant on the local draft. An initial attempt stopped at routing while Continue was disabled because the route configuration was incomplete; that setup timeout is not counted as a product defect. A follow-up pass used a single configured routing step, inspected settings and field placement, and continued through authentication and review to the final authorization screen. It stopped without clicking Authorize. Recipient signing, completed-request audit downloads and cancellation were not exercised in this pass. There was no send, signature submission, payment, reminder, production data mutation or production deployment.

Paid-plan screens, notary operations, complete recipient states, screen-reader behavior, real-device input, Firefox and Safari remain outside the verified coverage. The local replica uses local storage/scanning/email substitutes and has live identity integrations disabled. Do not turn those environment differences into product-feature requests or infer live-production failures from them.

## Decision

The reviewed baseline is not ready for a screen-quality sign-off because E01–E04 are confirmed accessibility defects. Address those first, then the existing-screen usability and motion work. Complete the remaining existing signing-flow checks before marking the whole product reviewed. This is a UI-quality recommendation, not a change to the running production service.
