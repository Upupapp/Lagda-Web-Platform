# Verification identity

**Command:** BACKEND-41 · **Exposed by:** BACKEND-42

## What it is

One opaque identifier per completed signing request, created in the finalization
transaction and stored on `verification_records` beside the seal it identifies.

## What it is NOT

- **Not a bearer credential.** Holding it authorizes nothing (§55, §137).
- **Not a download token.** Verification and document download are separate
  concerns, and BACKEND-42 must keep them separate (§159).
- **Not a secret.** It is intended to be public, so it is stored in ordinary
  form rather than as a digest — unlike every signing credential, which is
  stored digest-only precisely because it *is* a bearer token.

Classification: **PUBLIC-SAFE OPAQUE IDENTIFIER**, not SECRET.

## Created at finalization, not before

The command allows either (§53, §61). BACKEND-41 creates it in the finalization
transaction, and that choice **removed a mechanism rather than adding one**.

`verificationId` used to be an input to `DocumentSealer.seal()` so the
certificate could print it. BACKEND-40 removed that line — verification identity
belongs to BACKEND-41/42, and a certificate rendered before finalization has
none. That left the sealer destructuring a value it never read and echoing it
back, so BACKEND-41 removed it from the seam entirely.

Creating it during finalization means:

- **Retry stability is free.** The completion row is unique per request and the
  verification record is written in the same transaction, so exactly one
  identity can ever exist. §54 and §63 are satisfied by a constraint rather than
  by remembering to reuse a value.
- **No reservation mechanism is needed.** There is no "generated but unused"
  identity to track after a failed attempt, because none is generated until the
  attempt succeeds.

This works **only because nothing in the final bytes references it** — no QR, no
visual mark. If the product ever wants one, the identity must move earlier and
acquire a reservation, and that is a real cost to weigh at the time rather than
a detail to discover.

## Uniqueness

One per completed request, enforced by the uniqueness of the completion row and
the verification record's own key. There is exactly one canonical verification
identity — no separate certificate identity, seal identity or document identity
competing with it (§54).

## Entropy and enumeration

Generated by the canonical `VerificationIdGenerator`: opaque and
non-enumerable. BACKEND-42 must additionally ensure an unknown identifier fails
without distinguishing "no such record" from "not permitted" — otherwise the
lookup becomes an oracle for which identifiers exist.

## Handoff to BACKEND-42

Given a `verificationId`, BACKEND-42 can reach the seal, the final artifact's
authoritative SHA-256, the completion time, and the seal scheme and version.

It must project a **public-safe allowlist**, not a filtered row — recipient
names, emails, IP addresses, user agents, storage keys and internal identifiers
must not travel. `PublicVerificationProjection` already exists and is built by
naming each field rather than by omitting fields from a wider type, precisely so
a later addition cannot leak by default.
