# Sealing Architecture — BACKEND-09

## 1. What sealing is, and what it is not

Sealing takes a prepared PDF plus the values participants submitted, and produces
the artifacts LAGDA distributes and keeps:

- the **sealed document** — the source PDF with completed fields rendered onto it
- the **completion certificate** — a separate PDF recording who acted and when
- two **SHA-256 digests**, one for the prepared document, one for the sealed one

It does **not** apply a cryptographic signature. There is no PAdES, no PKCS#7, no
X.509 certificate, no timestamp authority, no HSM. The current seal scheme is
`hash-evidence`: integrity rests on LAGDA holding the digest of the exact bytes
distributed, plus the evidence log, not on a signature a third party can verify
offline.

This is not a shortfall against the specification. The backend integration
handoff contains **zero** occurrences of PAdES, PKCS, X.509, HSM, PNPKI or
RFC 3161 — checked, not assumed. Certificate-backed signing is a later decision
(OD-013), and the seam below is what keeps it a swap rather than a rewrite.

## 2. The seam

```
@lagda/application                      @lagda/sealing
┌──────────────────────────┐            ┌────────────────────────────┐
│ interface DocumentSealer │◄───────────│ class NodeDocumentSealer   │
│   seal(req): SealResult  │ implements │   ├── internal/digest      │
└──────────────────────────┘            │   ├── internal/fields      │
         ▲                              │   └── internal/certificate │
         │ depends on                   └────────────────────────────┘
   use cases                                        │ imports
                                                 pdf-lib
```

The port is **defined in application and implemented in sealing**. Application
never imports `@lagda/sealing`; the composition root injects the adapter. That
direction is what makes the implementation replaceable.

**One operation.** Not `mergeFields`, `hashDocument`, `renderCertificate`,
`appendPage`. Those exist as private collaborators inside the package. Every one
of them exposed on the port would be a call site a future remote signer has to
reproduce — and the reason a "seam" becomes a rewrite is that twenty callers each
learned a different piece of it.

## 3. Seal order

Fixed, and the order is load-bearing:

1. Validate the request (non-empty, PDF magic bytes).
2. **Hash the prepared document** — before anything can touch it.
3. Load the PDF, verifying it has a readable page tree and at least one page.
4. Validate every field's placement, then render them.
5. Serialize the sealed document.
6. **Hash the sealed document** — after every byte-changing step.
7. Render the certificate as a separate artifact.

Step 6 must not move. Hashing an intermediate buffer and publishing that digest
as final produces a verification page that fails against the document people are
actually holding — and it fails *silently*, because both values look like valid
digests.

## 4. Two hashes, named for their artifacts

`preparedDocumentHash` and `signedDocumentHash`. Never one field called `hash`.

An ambiguous name survives exactly as long as one person remembers which artifact
it referred to. The names also carry into persistence: when artifact metadata is
stored, the columns are `original_document_hash` and `signed_document_hash`.

Caveat, stated plainly: `Sha256Digest` is currently a plain alias for `string`,
unlike the branded ID types, so the two fields are mutually assignable and
swapping them would compile. The tests defend the ordering by comparing each
digest against one computed independently. Branding it is **OD-022**.

## 5. The certificate is a separate artifact

Handoff §15 stores "original PDF + signed PDF + completion certificate + evidence
log" — four things. So the certificate is **not** appended to the sealed
document.

Appending would change the signed document's page count, which means the file
delivered is no longer the file the participants reviewed and signed. A test
asserts the sealed output has the same page count as its source.

The certificate is a projection of the evidence, not the whole record. It carries
names, actions and timestamps. It deliberately does **not** carry IP addresses,
device fingerprints or location: the certificate ships to every participant, and
nothing in the specification asks for those to be shown to all of them.

## 6. Determinism

The sealer reads no clock, no randomness and no environment. `sealedAt` and
`verificationId` are supplied in the request.

`verificationId` is generated by the **application**, not here. Its specified
format is `LAGDA-{workspace}-{date}-{random}` — it contains randomness and it
belongs to LAGDA's identifier namespace. A sealer that minted it would be
non-deterministic, and a future remote signing service would own a namespace that
must remain LAGDA's.

An architecture test greps the package for `Date.now`, `new Date`, `Math.random`
and `process.env`, with comments stripped first so prose about clocks is not
mistaken for a clock read.

## 7. Errors

Six LAGDA-owned types, each with a stable `code` and a `retryable` flag. No
pdf-lib error reaches a caller.

`retryable` is not decoration. It is what stops the completion pipeline from
retrying a permanently malformed document forever. The distinction was not
theoretical: see §8.

| Error | Retryable | Means |
|---|---|---|
| `InvalidSealInputError` | no | The request itself is unusable — empty document. |
| `InvalidPdfError` | no | Not a PDF, unparseable, or no readable page tree. |
| `UnsupportedPdfError` | no | A valid PDF this implementation cannot process (encrypted). |
| `InvalidFieldPlacementError` | no | Bad page number or geometry. |
| `PdfProcessingError` | **yes** | Valid input, processing failed unexpectedly. |

## 8. A defect the tests found

pdf-lib's loader is tolerant. Bytes beginning `%PDF-1.7` followed by garbage
parse without complaint into a document with no page tree, and
`throwOnInvalidObject: true` does not change that. The failure then surfaced much
later, during font embedding, as a generic `PdfProcessingError` — marked
**retryable**.

So a permanently corrupt upload would have been retried indefinitely by the
completion pipeline, and every attempt would have failed identically.

The adapter now verifies the page tree immediately after load and classifies the
failure as `InvalidPdfError`. Reading the page count is itself guarded, because
on such a document `getPageCount()` throws a raw `TypeError` from inside the
library — an unguarded call there would have leaked a pdf-lib error through the
seam, which is exactly what INV-008 forbids.

## 9. What sealing does not do

- No object storage. Bytes come in as an argument and go out as a return value.
  A remote signer needs no knowledge of LAGDA's storage topology.
- No database. Nothing here reads or writes a row.
- No transaction. Sealing must never be called inside a database transaction:
  it is slow, it is external, and it cannot be rolled back when the commit fails.
- No identifier generation, no clock, no notifications.
- No decision about whether sealing is *allowed*. Whether a transaction is
  complete is a domain question and stays in `@lagda/core`.
